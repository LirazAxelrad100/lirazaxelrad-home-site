# Project: Liraz Axelrad personal site

## What it is
Personal site for Liraz Axelrad — product management + meditation + migration/life-transitions mentor. Astro + TypeScript + Tailwind CSS. Two independent language versions, not translations of each other:
- Hebrew (RTL) at `/` — primary/default language.
- English (LTR) at `/en`.

Both use the same menu-driven interactive homepage (click a menu item to open an inline info panel — no page navigation) built in `src/components/HomeMenu.tsx`, mounted as the site's only large client island (`client:load`) on `src/pages/index.astro` / `src/pages/en/index.astro`. Everything else on the site is static HTML with zero shipped JS, except the small `ContactForm.tsx` island on the Contact page.

Menu items live as Astro content collections — one Markdown file per item per locale (`src/content/menu/he/*.md`, `src/content/menu/en/*.md`), schema in `src/content.config.ts`. Adding/removing/reordering a menu item is adding/deleting a file or changing its `order` frontmatter number — no code editing required.

**Every menu item also has its own real page** (e.g. `/about`, `/pm`, `/meditation`, `/migration`, `/berlin`), rendered from that same Markdown file's body via a shared dynamic route (`src/pages/[item].astro`, `src/pages/en/[item].astro`) and `src/components/pages/MenuItemContent.astro`. The body is just paragraphs separated by a blank line — the **first paragraph** is pulled out (`src/lib/menu.ts`, `firstParagraph()`) and shown as the teaser in the homepage's grey panel; the full page shows every paragraph. So writing copy for an item is just writing paragraphs into its `.md` file — no separate excerpt field to keep in sync. Exception: English's "Writing" item (`src/content/menu/en/writing.md`) is excluded from this — its `href` points at the real `/en/writing` list instead, so it doesn't get one of these generic pages.

All other copy (name/tagline, Writing posts, Contact labels, footer) lives in `src/data/site.he.ts` / `site.en.ts` (shape in `src/data/types.ts`). About no longer has its own entry there — it's just another menu item now.

Original high-fidelity design prototype (static `.dc.html` files + handoff README) is preserved in `design/` for reference.

## Key decisions
- **Claude writes the code; Liraz reviews/tests in browser and handles all git commands herself** (add/commit/push) — for her portfolio, and her stated preference for this project.
- **On mobile, homepage menu items navigate straight to their own page instead of opening the teaser panel**, decided 2026-09-01 (commit `d8520e8`). Liraz spotted that below `md` the yellow panel renders *below* the menu, off-screen — so tapping an item looked like nothing happened, and she worried visitors would bounce. Options weighed were (a) navigate directly, or (b) replace the menu with the panel. Chose (a): the panel only ever holds the item's **first paragraph plus a "read more" link**, so (b) would still cost a second tap to reach content *and* would need a new back affordance to return to the other menu items. Implementation is deliberately tiny — each item was already a real `<a href={item.href}>`, and `HomeMenu.tsx`'s `onClick` simply skips `e.preventDefault()` when `window.matchMedia("(min-width: 768px)")` doesn't match, letting the browser navigate. 768px is Tailwind's `md`, the same breakpoint where the layout goes side-by-side, so the panel only opens when there's actually room beside the menu. Verified both ways: 375px navigates to `/pm`, 1280px stays home and opens the panel. Bonus: the links now work without JS. Desktop hover/click behavior is untouched — don't "unify" the two.
- **Footer stacks and centers below `md`; every footer link is `whitespace-nowrap`**, fixed 2026-09-01. Hebrew's footer has 6 links (contact + 4 socials + language mirror) vs English's 5, and at 375px labels like "English site" and "צרו קשר" were breaking *inside themselves* across 2 lines. Note the real fix was **not** a smaller font (Liraz's first instinct) — shrinking text keeps the mid-label breaks and just makes them harder to read. `Footer.astro`'s row is now `flex-col items-center text-center md:flex-row md:justify-between md:text-start`, the link group has its own `gap-x-4 gap-y-2 md:gap-5`, and each `<a>` is `whitespace-nowrap`. Desktop is byte-for-byte the same layout as before; the homepage's one-viewport-no-scroll constraint still holds (the fix actually *reduces* footer height, since 2-line labels collapse to 1).
- **`<ClientRouter />` (Astro view transitions) was REMOVED, 2026-09-01 — it broke the browser back button on iOS Safari.** Liraz reported that on her phone, going back from an item page (e.g. `/about`) exited the site entirely instead of returning to the homepage. It did **not** reproduce in the Chromium-based preview browser, where `/` → `/about` → back worked perfectly — so this is a genuine Safari-vs-Chromium difference in how Astro's router manipulates history, not a code bug you can see locally. Removed from `HtmlShell.astro` (import + tag) and **Liraz confirmed on her actual phone that back now works**. The cost is the page-to-page crossfade that was added 2026-08-21 — she explicitly chose a working back button over the fade. The `background: var(--color-bg)` on `html` (added in the same 2026-08-21 change, for first paint) is unrelated and stays. **Don't re-add `ClientRouter` without re-testing back navigation on a real iOS device** — the preview browser will not catch this.
- **Favicon: thin cream ring on a solid orange circle**, added 2026-09-01. Replaced the stock Astro placeholder (black circle + white triangle, 26KB). Liraz rejected letter-based marks — "LA" reads as Los Angeles, a lone "ל" felt arbitrary, "Axe" is illegible at 16px and is a deodorant brand in English. Landed on a pure shape in the site palette: ring `#fef3c7` on `#bb4d00`. **Two findings worth keeping:** (1) the ring *must* sit on a solid dark ground — a pale-yellow ring on transparent looks lovely on dark tab bars and is invisible on light ones, and you can't control what's behind a favicon; (2) stroke width is **optically hinted per size**, because Liraz's preferred thin stroke (0.045 of the icon width) is 0.7px at 16px and dissolves into a solid dot — so 16px uses 0.10, 32px 0.07, 48px 0.055, while the SVG and the 180px apple-touch icon get the true thin 0.045. Files: `public/favicon.svg` (vector), `public/favicon.ico` (16/32/48 bundled), `public/apple-touch-icon.png` (180, full-bleed **square** so iOS applies its own rounding instead of showing black corners) — all three wired up in `HtmlShell.astro`. Regenerate all three with `node scripts/make-icons.mjs public` — it draws and encodes everything itself (PNG via `zlib`, ICO container by hand, 4× supersampled edges) because there is no ImageMagick/rsvg on this machine. Output is deterministic, so re-running is safe and produces no diff. To change the colours or thickness, edit the constants at the top of that script and re-run — don't hand-edit the binaries, and never hand-copy base64 of a binary (it silently corrupts).
- **English footer socials: LinkedIn, Instagram, Facebook — deliberately no Substack**, 2026-09-01. The English LinkedIn/Instagram hrefs had been `#` placeholders (dead links on a live site); replaced with the same real URLs Hebrew uses. Substack is intentionally Hebrew-only in the footer because the Substack content is in Hebrew and wouldn't help English readers — that asymmetry is a decision, not an oversight.
- **Item body text is parsed as Markdown in both places it's shown**, fixed 2026-08-19. `MenuItemContent.astro` (the full page) already used `marked.parse()`; `HomeMenu.tsx` (the homepage teaser panel) was rendering the same string as plain text, so `[link](url)` syntax showed as literal brackets and wasn't clickable there. Now `HomeMenu` also parses the body, with `marked.parseInline()` (no wrapping `<p>`, since it's already inside one) — found when Liraz's new PM copy included a real Markdown link and it worked on `/en/pm` but not on the homepage panel. If you add bold/links/lists to any item's first paragraph, they'll now render correctly in both places.
- **Astro over Next.js**, decided 2026-08-16. Reasoning: the site is ~95% static content with one interactive homepage menu and a contact form — Astro ships zero JS by default and only hydrates those two pieces ("islands"), instead of shipping a full React runtime for a page that doesn't need it. It also lets menu items live as individual Markdown files (content collections) instead of entries in a TypeScript array, which is easier for Liraz (non-developer) to add/edit/remove herself.
- **Not a translation-key i18n setup**, still true post-migration. Each locale has its own independent content (menu order, item count, copy can all differ). Not using Astro's built-in i18n routing, which assumes translated parity — instead, plain duplicate route trees per locale, same approach as before.
- **Routing:** Hebrew pages live at `src/pages/*.astro` (site root); English pages live at `src/pages/en/*.astro` (adds `/en` prefix) — direct analog of the old Next.js route-group setup, just as separate files rather than a route-group folder trick.
- **Rendering:** `output: "static"` — every page is prerendered at build time except `src/pages/api/contact.ts`, which opts out via `export const prerender = false` and runs as an on-demand serverless function (Vercel adapter) only when the contact form is submitted.
- **Fonts:** self-hosted via Fontsource packages (`@fontsource-variable/rubik`, `@fontsource/david-libre`, `@fontsource-variable/heebo`) instead of `next/font/google` — same fonts, no Next-specific API.
- **Homepage-only compact spacing:** `Footer` takes an optional `compact` prop, used only on the homepage. `Header` is not a shared component on the homepage anymore — its markup lives inline inside the `HomeMenu` island (needed for the "click name to reset the open panel" interaction), while content pages use the static `Header.astro`. This exists because Liraz found the homepage specifically felt oversized/required scrolling, while About/Writing/Contact felt fine as-is — so sizing was tuned per-surface, not globally. Don't collapse this back into one shared size.
- **Homepage fills exactly one viewport, no scroll, symmetric top/bottom gap.** Fixed 2026-08-16 (post-migration): the page wrapper is `h-screen` (not `min-h-screen`), and inside `HomeMenu` the header is `flex-shrink-0` while the nav/panel row is `flex-1` — that row's existing `justify-center` on `<nav>` then centers the menu vertically in whatever space is left between header and footer, making the two gaps equal automatically. Note this reverses an earlier Next.js-era decision to avoid `flex-1` there (that one was about the now-deleted hover-image column interacting badly with it — with that column gone, `flex-1` is now correct and intentional). Don't reintroduce a min-height/fixed-height column here without re-checking this still holds.
- **Content frontmatter is hand-written YAML — watch for stray Hebrew punctuation.** Hit 2026-08-20: `he/meditation.md`'s `title` field was opened with a straight `"` but accidentally closed with a Hebrew gershayim `״` (visually similar, different character), which broke YAML parsing (`glob-loader` reload error: "can not read a block mapping entry"). If a content file fails to load with a YAML error like that, check for a mismatched quote character before anything else — easy to introduce when typing Hebrew, since gershayim/geresh look almost identical to `"`/`'` at a glance.
- **Hover-image reveal was never built and stays out of scope.** The original design intent (grayscale→color image reveal on menu hover, documented in `design/README.md`) was never implemented in the Next.js version either — the `image` field was carried in the data but unused. Dropped from the new content schema entirely rather than porting a dead field. Revisit only if explicitly requested.
- **Contact is not a homepage menu item.** Decided 2026-08-16: a numbered menu panel was too much weight for a contact form. Contact is reachable via a plain link in the footer (`footer.contactLabel`/`footer.contactHref` in the site data) plus the existing `mailto:` link; the `/contact` page and form still work exactly as before.
- **"Berlin, Berlin!" is a real, intentional menu item** (not a mistake) — it replaced what used to be the "Writing" menu entry in both locales, keeping that item's original panel copy/link/CTA, just relabeled. - **Sequencing was deliberately changed from the original plan.** The old plan was "transfer the registrar first, then point DNS at Vercel," which would have meant waiting 5–7 days before the site was live on the real domain. Cloudflare DNS and Cloudflare Registrar are independent — and Email Routing only requires the domain to be on Cloudflare *nameservers*, not registered there, so the `hello@` inbox is unblocked by the DNS move alone.
- **DNS records now in Cloudflare** (both **DNS-only / grey cloud** — proxying would break Vercel's cert):
  - `A` `@` → `216.198.79.1`
  - `CNAME` `www` → `8436b98fdcb2f138.vercel-dns-017.com`
  - Vercel's dashboard is the source of truth for these. `216.198.79.1` is their newer IP range; the widely-quoted `76.76.21.21` / `cname.vercel-dns.com` are legacy (still work, but don't assume them). The `www` CNAME target is **project-specific** — always read it off Settings → Domains → View DNS configuration rather than guessing.
- **The 4 old WordPress records were deleted**: two `A` at apex → `192.0.78.24`/`.25`, a wildcard `CNAME *`, and `CNAME www`. Nameservers at WordPress.com changed from `ns1/2/3.wordpress.com` to `osmar.ns.cloudflare.com` + `uma.ns.cloudflare.com` (Domains → the domain → Settings → Name servers → toggle off "Use WordPress.com name servers").
- **Canonical is the bare domain, not `www`.** Vercel defaulted to the opposite (apex 308 → www); flipped so `lirazaxelrad.com` is the Production domain and `www` redirects to it. This matters because `astro.config.mjs` uses `site: process.env.PUBLIC_SITE_URL || "https://lirazaxelrad.com"`, so sitemap/hreflang URLs are bare-domain — the other direction would have made every sitemap URL a redirect. If the canonical is ever changed, change both places together.
- **Cloudflare's own resolver (1.1.1.1) was the last one to pick up the new nameservers**, well after `8.8.8.8` and `9.9.9.9` had. That's what delays the zone flipping to "Active" in the Cloudflare dashboard — it's a cache timer, not a misconfiguration. Verify propagation with `dig +noall +authority NS <domain> @a.gtld-servers.net` (the authoritative TLD delegation) rather than trusting any single resolver.
- **DNSSEC was already off** (`whois` → `DNSSEC: unsigned`) so no action was needed. Worth checking before any nameserver change — DNSSEC left on across a nameserver switch breaks the domain hard.
- **Liraz's own machine kept showing the OLD WordPress site for hours after the switch — this is her router/ISP cache, not a site problem.** Her Mac resolves via `192.168.0.1` (the router), which forwards to her ISP, which held the stale answer long after Google/Quad9/OpenDNS had all updated. Diagnose by comparing resolvers (`dig +short NS lirazaxelrad.com @8.8.8.8` etc.) against the authoritative delegation (`dig +noall +authority NS lirazaxelrad.com @a.gtld-servers.net`), and verify the real site with `curl --resolve lirazaxelrad.com:443:216.198.79.1 ...` to bypass DNS entirely. Fix is to set her Mac's DNS to `8.8.8.8`/`9.9.9.9`, restart the router, or wait (worst case ~48h, the TTL on the old delegation). **Do not suggest `1.1.1.1`** — Cloudflare's own public resolver was the very last one still serving the stale record.
