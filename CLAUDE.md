# Project: Liraz Axelrad personal site

## What it is
Personal site for Liraz Axelrad — product management + meditation + migration/life-transitions mentor. Astro + TypeScript + Tailwind CSS. Two independent language versions, not translations of each other:
- Hebrew (RTL) at `/` — primary/default language.
- English (LTR) at `/en`.

Both use the same menu-driven interactive homepage (click a menu item to open an inline info panel — no page navigation) built in `src/components/HomeMenu.tsx`, mounted as the site's only large client island (`client:load`) on `src/pages/index.astro` / `src/pages/en/index.astro`. Everything else on the site is static HTML with zero shipped JS, except the small `ContactForm.tsx` island on the Contact page.

Menu items live as Astro content collections — one Markdown file per item per locale (`src/content/menu/he/*.md`, `src/content/menu/en/*.md`), schema in `src/content.config.ts`. Adding/removing/reordering a menu item is adding/deleting a file or changing its `order` frontmatter number — no code editing required.

**Every menu item also has its own real page** (e.g. `/about`, `/pm`, `/meditation`, `/migration`, `/berlin`), rendered from that same Markdown file's body via a shared dynamic route (`src/pages/[item].astro`, `src/pages/en/[item].astro`) and `src/components/pages/MenuItemContent.astro`. The body is just paragraphs separated by a blank line — the **first paragraph** is pulled out (`src/lib/menu.ts`, `firstParagraph()`) and shown as the teaser in the homepage's grey panel; the full page shows every paragraph. So writing copy for an item is just writing paragraphs into its `.md` file — no separate excerpt field to keep in sync. Exception: English's "Writing" item (`src/content/menu/en/writing.md`) is excluded from this — its `href` points at the real `/en/writing` list instead, so it doesn't get one of these generic pages.

All other copy (name/tagline, Writing posts, Contact labels, footer) lives in `src/data/site.he.ts` / `site.en.ts` (shape in `src/data/types.ts`). About no longer has its own entry there — it's just another menu item now.

Original high-fidelity design prototype (static `.dc.html` files + handoff README) is preserved in `design/` for reference.

Repo: https://github.com/LirazAxelrad100/lirazaxelrad-home-site

## Key decisions
- **Claude writes the code; Liraz reviews/tests in browser and handles all git commands herself** (add/commit/push) — for her portfolio, and her stated preference for this project.
- **Item body text is parsed as Markdown in both places it's shown**, fixed 2026-08-19. `MenuItemContent.astro` (the full page) already used `marked.parse()`; `HomeMenu.tsx` (the homepage teaser panel) was rendering the same string as plain text, so `[link](url)` syntax showed as literal brackets and wasn't clickable there. Now `HomeMenu` also parses the body, with `marked.parseInline()` (no wrapping `<p>`, since it's already inside one) — found when Liraz's new PM copy included a real Markdown link and it worked on `/en/pm` but not on the homepage panel. If you add bold/links/lists to any item's first paragraph, they'll now render correctly in both places.
- **Astro over Next.js**, decided 2026-08-16. Reasoning: the site is ~95% static content with one interactive homepage menu and a contact form — Astro ships zero JS by default and only hydrates those two pieces ("islands"), instead of shipping a full React runtime for a page that doesn't need it. It also lets menu items live as individual Markdown files (content collections) instead of entries in a TypeScript array, which is easier for Liraz (non-developer) to add/edit/remove herself.
- **Not a translation-key i18n setup**, still true post-migration. Each locale has its own independent content (menu order, item count, copy can all differ). Not using Astro's built-in i18n routing, which assumes translated parity — instead, plain duplicate route trees per locale, same approach as before.
- **Routing:** Hebrew pages live at `src/pages/*.astro` (site root); English pages live at `src/pages/en/*.astro` (adds `/en` prefix) — direct analog of the old Next.js route-group setup, just as separate files rather than a route-group folder trick.
- **Rendering:** `output: "static"` — every page is prerendered at build time except `src/pages/api/contact.ts`, which opts out via `export const prerender = false` and runs as an on-demand serverless function (Vercel adapter) only when the contact form is submitted.
- **Fonts:** self-hosted via Fontsource packages (`@fontsource-variable/rubik`, `@fontsource/david-libre`, `@fontsource-variable/heebo`) instead of `next/font/google` — same fonts, no Next-specific API.
- **Homepage-only compact spacing:** `Footer` takes an optional `compact` prop, used only on the homepage. `Header` is not a shared component on the homepage anymore — its markup lives inline inside the `HomeMenu` island (needed for the "click name to reset the open panel" interaction), while content pages use the static `Header.astro`. This exists because Liraz found the homepage specifically felt oversized/required scrolling, while About/Writing/Contact felt fine as-is — so sizing was tuned per-surface, not globally. Don't collapse this back into one shared size.
- **Homepage fills exactly one viewport, no scroll, symmetric top/bottom gap.** Fixed 2026-08-16 (post-migration): the page wrapper is `h-screen` (not `min-h-screen`), and inside `HomeMenu` the header is `flex-shrink-0` while the nav/panel row is `flex-1` — that row's existing `justify-center` on `<nav>` then centers the menu vertically in whatever space is left between header and footer, making the two gaps equal automatically. Note this reverses an earlier Next.js-era decision to avoid `flex-1` there (that one was about the now-deleted hover-image column interacting badly with it — with that column gone, `flex-1` is now correct and intentional). Don't reintroduce a min-height/fixed-height column here without re-checking this still holds.
- **Content frontmatter is hand-written YAML — watch for stray Hebrew punctuation.** Hit 2026-08-20: `he/meditation.md`'s `title` field was opened with a straight `"` but accidentally closed with a Hebrew gershayim `״` (visually similar, different character), which broke YAML parsing (`glob-loader` reload error: "can not read a block mapping entry"). If a content file fails to load with a YAML error like that, check for a mismatched quote character before anything else — easy to introduce when typing Hebrew, since gershayim/geresh look almost identical to `"`/`'` at a glance.
- **Hover-image reveal was never built and stays out of scope.** The original design intent (grayscale→color image reveal on menu hover, documented in `design/README.md`) was never implemented in the Next.js version either — the `image` field was carried in the data but unused. Dropped from the new content schema entirely rather than porting a dead field. Revisit only if explicitly requested.
- **Contact is not a homepage menu item.** Decided 2026-08-16: a numbered menu panel was too much weight for a contact form. Contact is reachable via a plain link in the footer (`footer.contactLabel`/`footer.contactHref` in the site data) plus the existing `mailto:` link; the `/contact` page and form still work exactly as before.
- **"Berlin, Berlin!" is a real, intentional menu item** (not a mistake) — it replaced what used to be the "Writing" menu entry in both locales, keeping that item's original panel copy/link/CTA, just relabeled. (While porting, found the Hebrew content file had accidentally applied this label to the *Contact* item instead of the *Writing* item — fixed during migration so both locales consistently apply it to Writing.)
- **English menu had "Migration & Growth" temporarily replaced by "Writing"; both are back now.** Changed 2026-08-16 to free the slot for Writing while Migration's copy wasn't written yet — noted at the time as **not a final decision**. Resolved 2026-08-24: Liraz added Migration back as its own English menu item (`src/content/menu/en/migration.md`, `order: 4`) with real copy, so the English menu is now 6 items (About, PM, Meditation, Migration, Writing, Berlin) — no longer asymmetric with Hebrew on this point.
- **Every menu item gets its own dedicated page; About's "What I do" grid is dropped.** Decided 2026-08-16, resolving the earlier open question about Migration/PM lacking real pages. Every item (About, PM, Meditation, Migration, Berlin) now follows one consistent pattern — title + paragraphs, first paragraph doubles as the homepage teaser — instead of most of them stand-in-linking to `/about`. The old About-only "What I do" 3-item grid was intentionally removed rather than kept as a special case, so all item pages are now structurally identical. See the content-collections paragraph above for how this is wired.
- Subscribe link was removed entirely (not wanted). RSS icon lives in the footer only, positioned direction-aware (`dir`) via start/end, not a fixed side — intentional mirroring between locales, not a bug.
- Node.js wasn't installed on this machine — installed via nvm (`~/.nvm`, default alias is v24.19.0). If commands like `npm`/`node` aren't found in a fresh shell, `nvm`'s init lines are in `~/.zshrc`.
- **Domain will move from WordPress to Cloudflare (registrar + DNS), not just repoint DNS.** Decided 2026-08-23. `lirazaxelrad.com` is currently registered through WordPress.com with a blog hosted there (OK to lose — export via WordPress.com's Export tool first if any posts are worth keeping). Plan: transfer the domain registration itself to Cloudflare (get EPP/auth code from WordPress, unlock the domain, initiate transfer from Cloudflare's dashboard — takes ~5-7 days, blocked if registered/transferred in the last 60 days), then manage DNS in Cloudflare pointing to Vercel. DNS records to Vercel should be **DNS-only (grey cloud), not proxied** — Vercel issues its own per-domain SSL cert, which can conflict with Cloudflare's proxy layer. Audience is mainly Israel + Berlin/EU, and Vercel's edge network already covers both well, so Cloudflare's CDN/proxy isn't needed for performance, just registrar + DNS management.
- **Site analytics not yet chosen** — discussed 2026-08-23. Since the new site is static (no built-in analytics), need to add one at deploy time: leaning toward Plausible/Fathom (privacy-friendly, no cookie banner needed, fits the zero-JS philosophy) over Google Analytics (free but heavier, needs EU cookie consent). Not decided — revisit when deploying. Also add the site to **Google Search Console** post-deploy (verify domain, submit `sitemap.xml`) — that's what gets it indexed and gives search performance data.
